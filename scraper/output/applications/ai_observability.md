# AI Observability

- [](/_docs/)- Applications- AI ObservabilityOn this page# AI Observability
The TRiSM hub provides and AI observability layer. The core technology for the observability layer is an OpenSearch service that runs on your plane and maintains AI logs within your AWS account. Events that pertain to various activities on the system are funneled into this observability layer. You can then use both out-of-the-box dashboards as well as build your own dashboards and reports that use this data. The TRiSM Hub embeds a fully-integrated AWS-provided OpenSearch service. The service works within the authentication and authorization models and is embedded within the GUI. It is a fully-functioning OpenSearch service providing openness, extensibility and ability to customize. For more information on the APIs and capabilities afforded by this service [click here](https://docs.aws.amazon.com/opensearch-service/)

For information on how to use dashboards, visualizations, alerting and anomaly detection please refer to the OpenSearch documentation.

You can use APIs in order to funnel additional data from your own AI and AI-related systems to the observability layer.

Finally, you can configure the system to send AI gateway events (prompts and responses) to Datadog's LLM Observability layer thus providing LLM visibility without needing to add Datadog instrumentation code to your applications.

Note that because the observability layer is all about seeing all information in the AI data lake, the organization/project pull-down menu does not affect what data you see. You will see information pertaining to all projects (that you are allowed to see).

By default the observability layer's retention policy is three months (in the index) and six months in S3/raw files. Contact your account manager to request different retention policies.

## Data Sets / Indexes[​](#data-sets--indexes)
The following indexes are predefined within the system:

- ai-inventory - Include events generated by the AI discovery and inventory subsystem.
- ai-ocsf-firewall - Include events generated by the AI gateway. Events comply with the OCSF standard format.
- ai-ocsf-spm - Include events generated by the AI Security Posture Management subsystem.
- ai-issues - Includes all issues flagged by the system, from all applications.
- ai-incidents - Includes incident events generated by the system.

In addition, the following indexes are accessible by admins and pertain to the operations of the system itself:

- ai-scheduled-jobs - Includes start and end events for scheduled jobs such as model and LLM scans.
- ai-activity-trail - Includes all actions performed by users on the systems.

## Dashboard[​](#dashboard)
The dashboard provides an overview of security events related to your AI systems and specifically metrics about security events generated by the AI gateway and security posture events.

## Evaluate[​](#evaluate)
The evaluation system is used to run side-by-side comparisons of different profiles. You define one or more evaluations (e.g. accessing different endpoints, running things through the AI Gateway, etc) and multiple tests. You then run the evaluation and analyze the differences between the runs. You can evaluate any endpoint - including custom endpoints (your applications). Check the "Enable Active Gateway Policies" to run the tests through the guardrails. Evaluation types include various pass/fail evaluation criteria, custom evaluations using LLM-as-a-judge, correctness, sentiment, robustness and more.

## Datasets[​](#datasets)
A Dataset is a set of prompts that were observed within the Observability system (i.e. were processed by the AI Gateway). Create a dataset as a way to "teach" other parts of the system how your application behaves and make the system adapt to your applications. For example, use a Dataset to fine-tune a pentest to your application's observed behavior.

Create a Dataset by applying various filters (the most common ones are time based filters and a particular endpoint), click the Run Data Search button, and then select/add from Found Requests to Added Requests. Then give the Dataset a name, description and assign it to a project.

## Permissions in the Observability Layer[​](#permissions-in-the-observability-layer)
There are two dimensions with which you control how users can see data stored in OpenSearch.

The first is role based. As in other parts of the system, you manage access using roles as defined [here](/_docs/platform_services/account_mgmt). The system has built-in roles pertaining to each of the data categories in the OpenSearch indexes (e.g. ai-ocsf-firewall vs. ai-ocsf-spm) allowing you to provide access appropriately.

Available roles for controlling OpenSearch authorization:

- Observability Admin - full access
- Observability Viewer - read only access
- Observability Editor - ability to edit and view reports, dashboards, visualizations, alerts and detectors
- Observability Auditor - access only the internal audit trail and scheduled jobs run indexes for search and reporting

In addition, you control which specific documents a user can see (Document Level Security / DLS) using organizations and projects. Because each document in the indexes includes an organization and a project for which the event was created (when this is relevant), and because you control which projects and organizations users have access to [here](/_docs/overview/orgs_and_projects), you can ensure that even when users have roles that give them access to a particular function that they can only see data from the appropriate source.

## Alerts[​](#alerts)
To use alerts navigate to the Threat Detection -&gt; Alerts tab.

Alerts are part of OpenSearch and documented [here](https://opensearch.org/docs/latest/observing-your-data/alerting/index/).

## Threat Detection[​](#threat-detection)
To use alerts navigate to the Threat Detection -&gt; Anomaly Detection.

Anomaly detection capabilities are a part of OpenSearch and documented [here](https://opensearch.org/docs/latest/observing-your-data/ad/index/).

Additionally, some anomaly detectors are available as part of the system. Click on Detectors to see all predefined algorithms. The prebuilt anomaly detection algorithms work off the ai-ocsf-index and analyze threats related to LLM access based on the events logged by the AI gateway. These can be enabled as shipped or can be cloned and modified based on your requirements.

## Search[​](#search)
Use the search tab to select an index, and run any query to view events being collected within the AI observability data lake. Documentation on how to analyze data is [here](https://opensearch.org/docs/latest/dashboards/discover/index-discover/)

## Custom Log Ingestion[​](#custom-log-ingestion)
You can ingest any additional data into the OpenSearch AI Data Lake. Your data plane has an S3 bucket which is a landing area for any custom logs. When you drop files into this S3 bucket they are ingested and indexed within OpenSearch, allowing you to search, build reports, build dashboards and use anomaly detection. The ingestion service looks for folders within the S3 bucket. Folder names are used as the index names (for example, if you create a folder called MLDataSetAccess then an index by that name will be created automatically). Indexes will include all events from all files you copy into this folder. Ingestion is event-based; when a new file appears in any of these folders it is ingested and events are inserted into the index. Files remain within the folders for a month, after which they are archived to Glacier (using standard S3 lifecycle rules).

All capabilities of OpenSearch apply to these custom indexes. You can create the index, refresh fields, create index patterns etc. if you have the ObservabilityAdministrator role. When the data plan runs within your account (as opposed to running within the Varonis Cloud), log into the AWS console for this account and look for the bucket called `alltruecustomerplane-alltruecustomerbucket-&lt;RANDOM_ID&gt;`; this is where you should create folders and copy files into. If the data plane is running within the Varonis Cloud contact your account manager to get access to the bucket.
