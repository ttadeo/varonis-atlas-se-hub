# AI Observability

- [](/_docs/)- Applications- AI ObservabilityOn this page# AI Observability
The TRiSM Hub provides an AI observability layer that runs on a Data Plane deployed within your own AWS or Azure cloud account. Once installed, the Data Plane captures and maintains AI activity logs inside your tenant, ensuring that telemetry stays within your security boundary. Events relating to AI usage, runtime protection, and investigation activities are funneled into this observability layer, where they power the Hub's monitoring and analysis capabilities.

The observability layer comes with a set of built-in dashboards that surface key signals out of the box, and it also exposes the underlying log data so you can build your own dashboards, visualizations, and reports tailored to your organization's needs. Because the Data Plane is provisioned directly in your cloud account (via CloudFormation on AWS or the equivalent deployment on Azure) and operates within the TRiSM Hub's authentication and authorization model, all access to logs, dashboards, and analytics is governed by the same role-based controls used elsewhere in the product.

You can use APIs in order to funnel additional data from your own AI and AI-related systems to the observability layer.

Finally, you can configure the system to send AI Runtime Protection events (prompts and responses) to Datadog's LLM Observability layer, providing LLM visibility without needing to add Datadog instrumentation code to your applications.

Note that because the observability layer is designed to surface all information in the AI data lake, the organization/project dropdown does not affect what data you see. You see information pertaining to all projects that you are allowed to access.

By default, the observability layer's retention policy is three months (in the index) and six months in S3/raw files. Contact your account manager to request different retention policies.

## Data Sets / Indexes[​](#data-sets--indexes)
The following indexes are predefined within the system:

- ai-inventory - Includes events generated by the AI discovery and inventory subsystem.
- ai-ocsf-firewall - Includes events generated by the AI Runtime Protection. Events comply with the OCSF standard format.
- ai-ocsf-spm - Includes events generated by the AI Security Posture Management subsystem.
- ai-issues - Includes all issues flagged by the system, from all applications.
- ai-incidents - Includes incident events generated by the system.

In addition, the following indexes are accessible by admins and pertain to the operations of the system itself:

- ai-scheduled-jobs - Includes start and end events for scheduled jobs such as model and LLM scans.
- ai-activity-trail - Includes all actions performed by users on the system.

## Dashboard[​](#dashboard)
The dashboard provides an overview of security events related to your AI systems and specifically metrics about security events generated by the AI Runtime Protection and security posture events.

## Evaluate[​](#evaluate)
The evaluation system is used to run side-by-side comparisons of different profiles. You define one or more evaluations (e.g., accessing different endpoints, running requests through the AI Runtime Protection) and multiple tests. You then run the evaluation and analyze the differences between runs. You can evaluate any endpoint, including custom endpoints (your applications). Check "Enable Active Runtime Policies" to run the tests through the guardrails. Evaluation types include various pass/fail criteria, custom evaluations using LLM-as-a-judge, correctness, sentiment, robustness, and more.

## Datasets[​](#datasets)
A Dataset is a set of prompts that were observed within the Observability system (i.e., were processed by the AI Runtime Protection). Create a dataset as a way to "teach" other parts of the system how your application behaves and help the system adapt to your applications. For example, use a Dataset to fine-tune a pentest to your application's observed behavior.

Create a Dataset by applying various filters (the most common are time-based filters and a particular endpoint), click **Run Data Search**, and then select and add from Found Requests to Added Requests. Then give the Dataset a name and description, and assign it to a project.

## Permissions in the Observability Layer[​](#permissions-in-the-observability-layer)
There are two dimensions with which you control how users can see data stored in OpenSearch.

The first is role-based. As in other parts of the system, you manage access using roles as defined [here](/_docs/platform_services/account_mgmt). The system has built-in roles pertaining to each of the data categories in the OpenSearch indexes (e.g., ai-ocsf-firewall vs. ai-ocsf-spm), allowing you to provide access appropriately.

Available roles for controlling OpenSearch authorization:

- Observability Admin - Full access
- Observability Viewer - Read-only access
- Observability Editor - Ability to edit and view reports, dashboards, visualizations, alerts, and detectors
- Observability Auditor - Access only to the internal audit trail and scheduled job indexes for search and reporting

In addition, you control which specific documents a user can see (Document Level Security / DLS) using organizations and projects. Because each document in the indexes includes the organization and project for which the event was created (when applicable), and because you control which projects and organizations users have access to [here](/_docs/overview/orgs_and_projects), you can ensure that users only see data from the sources they are authorized to access, even when their roles grant access to a particular function.

## Alerts[​](#alerts)
To use alerts, navigate to Threat Detection -&gt; Alerts.

Alerts are part of OpenSearch and documented [here](https://opensearch.org/docs/latest/observing-your-data/alerting/index/).

## Threat Detection[​](#threat-detection)
To use anomaly detection, navigate to Threat Detection -&gt; Anomaly Detection.

Anomaly detection capabilities are part of OpenSearch and documented [here](https://opensearch.org/docs/latest/observing-your-data/ad/index/).

Additionally, some anomaly detectors are available as part of the system. Click **Detectors** to see all predefined algorithms. The prebuilt anomaly detection algorithms work off the ai-ocsf-index and analyze threats related to LLM access based on events logged by the AI Runtime Protection. These can be enabled as-is or cloned and modified based on your requirements.

## Search[​](#search)
Use the Search tab to select an index and run any query to view events collected within the AI observability data lake. Documentation on how to analyze data is available [here](https://opensearch.org/docs/latest/dashboards/discover/index-discover/).

## Custom Log Ingestion[​](#custom-log-ingestion)
You can ingest any additional data into the OpenSearch AI Data Lake. Your data plane has an S3 bucket that serves as a landing area for custom logs. When you drop files into this S3 bucket, they are ingested and indexed within OpenSearch, allowing you to search, build reports and dashboards, and use anomaly detection. The ingestion service looks for folders within the S3 bucket. Folder names are used as the index names (for example, if you create a folder called MLDataSetAccess, an index by that name is created automatically). Indexes include all events from all files you copy into that folder. Ingestion is event-based: when a new file appears in any of these folders, it is ingested and events are inserted into the index. Files remain within the folders for a month, after which they are archived to Glacier using standard S3 lifecycle rules.

All capabilities of OpenSearch apply to these custom indexes. You can create the index, refresh fields, create index patterns, etc. if you have the ObservabilityAdministrator role. When the data plane runs within your account (as opposed to running within the Varonis Cloud), log into the AWS console for this account and look for the bucket called `alltruecustomerplane-alltruecustomerbucket-&lt;RANDOM_ID&gt;`; this is where you should create folders and copy files. If the data plane is running within the Varonis Cloud, contact your account manager to get access to the bucket.
