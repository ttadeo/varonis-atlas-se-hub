# SIEM Integrations

- [](/_docs/)- [Admin Console](/_docs/docs/admin_console/)- SIEM IntegrationsExport PDFOn this page# SIEM Integrations
Use SIEM integrations to send Atlas issue, incident, and supported runtime events to external security tools. Go to **Admin Console &gt; System Settings &gt; SIEM** to add an integration endpoint and choose, per project, which event types are forwarded to that endpoint.

Supported endpoint choices in the Admin Console are:

- Splunk (uses Splunk HEC as the transport)
- Datadog
- Panther
- MS Sentinel

Setup follows a two-step model:

- On the **Integrations** tab, you add a SIEM integration endpoint with provider credentials.
- On the **Configuration** tab, you choose, for each project, which event types flow to which endpoint.

Routing AI incidents to ServiceNow, Email, or Jira is configured separately on the [Service Management](/_docs/docs/admin_console/service_management) page; SIEM and Service Management are independent integrations.

## How SIEM forwarding works[​](#how-siem-forwarding-works)
SIEM forwarding has two configuration surfaces and one background delivery worker.

When you add an integration on the **Integrations** tab, Atlas stores the endpoint's provider credentials and exposes the endpoint to every project. When you add a configuration on the **Configuration** tab for a project, you choose which of that endpoint's supported event categories should be forwarded for that project.

The Panther provider type is exposed as a Panther / any HTTPS / API Bearer-authentication endpoint. This is what lets customers piggyback other Bearer-authenticated HTTP receivers — for example IBM QRadar — on the Panther provider type. See [QRadar Integration](#qradar-integration) below for the full walkthrough.

Three families of events can be forwarded, depending on what the selected provider supports:

- **Issue events** — created and updated issue events generated by Atlas. You can forward all issue types or only selected issue types.
- **Incident events** — created incident events; whether incident updates are also forwarded depends on the provider (see the matrix below).
- **Runtime events** — provider-dependent. Currently, runtime prompt input and output forwarding is supported only for Datadog as part of LLM observability.

Outbound delivery is asynchronous. A background worker batches pending events, sends them to the configured endpoint, and records each outbound event as either **SENT** or **ERROR**. The **Last Activity** column on the Integrations table reflects the most recent successful send for that endpoint.

## Prerequisites[​](#prerequisites)
Before you set up a SIEM integration, verify that you have:

- Access to the Admin Console in Atlas.
- Permission to manage SIEM integrations in the Admin Console.
- Provider credentials prepared in advance for the SIEM you plan to add:

**Splunk** — HEC token and endpoint URL.
- **Datadog** — Host, API Key, and Application Key.
- **Panther** — log source URL and token.
- **MS Sentinel** — Access Token URL, Client ID, Client Secret, Issue Receiver Endpoint, and Incident Receiver Endpoint (OAuth2 client-credentials flow against Sentinel's data-collection endpoints).

- At least one project for which you want to forward events.

## Add a SIEM integration[​](#add-a-siem-integration)
Add an endpoint from the **Integrations** tab. Each endpoint is created once and can then be reused across projects from the Configuration tab.

- Go to **Admin Console &gt; System Settings &gt; SIEM**.
- Open the **Integrations** tab.
- Click **Add Integration**.
- In the provider picker, choose one of **Splunk**, **Datadog**, **Panther**, or **MS Sentinel**.
- Fill in the provider credential fields using the labels shown on the form. Credential values are stored masked.
- Click **Save**. Atlas validates the credentials with the provider. If validation fails, the form surfaces the error inline.

After save, the new endpoint appears in the Integrations table. The table shows the integration name, the provider, the **Last Activity** timestamp (most recent successful outbound delivery), and the projects currently forwarding events to this endpoint.

You can edit an existing endpoint to update its credentials, and you can delete an endpoint when it is no longer needed. Edit and delete actions show confirmation toasts. Deleting an endpoint removes all per-project configurations that targeted it.

## Configure project events[​](#configure-project-events)
After an endpoint exists, choose what flows to it for each project. Configurations are scoped to a single project; if you want the same forwarding behavior for multiple projects, add a configuration to each.

- Go to **Admin Console &gt; System Settings &gt; SIEM**.
- Open the **Configuration** tab.
- Use **Select Project** to choose the project you want to configure.
- Click **Add Configuration**.
- In the dialog, choose a **SIEM Integration** from the selector. The selector lists only endpoints created on the Integrations tab. If every available integration has already been configured for the selected project, the action is disabled and labeled **All Integrations Configured**.
- Toggle the event categories you want to forward to that endpoint: **Issue events**, **Incident events**, and **Runtime events** (where the provider supports it).
- If you enable issue forwarding, use the **Issue Types** selector to forward all issue types or only selected ones.
- For Datadog runtime forwarding, you can independently toggle **Send Input Runtime Prompts** and **Send Output Runtime Prompts** to control which sides of LLM traffic are exported.
- Click **Save**. The configuration appears in the configuration table for the selected project.

Each project's configuration table shows the SIEM Integration name, the event categories enabled, and the source label that identifies how the configuration was created. From the table you can edit or delete each configuration. Edits and deletes are scoped to the current project and do not affect other projects forwarding to the same endpoint.

## Verify delivery and troubleshoot[​](#verify-delivery-and-troubleshoot)
After you save an integration and configure project events, use these signals to verify delivery:

- **Inline validation errors.** Credential validation runs when you save an integration. If credentials are wrong or the provider rejects them, the form shows the error inline. Fix the credentials and save again.
- **Last Activity timestamp.** On the Integrations tab, the **Last Activity** column updates after a successful outbound send. Trigger an issue or incident in the configured project and wait briefly for the timestamp to advance.
- **Outbound event status.** Each outbound event is tracked individually as **SENT** or **ERROR**. Errored events do not advance the Last Activity timestamp.
- **Expected delay.** Outbound delivery is asynchronous and batched. Events typically reach the destination within a short delay rather than instantly.

If events are not arriving:

- Confirm the integration's **Last Activity** is recent. If it never advances, credentials or network reachability are the most likely cause.
- Confirm the project configuration includes the event categories you expect. For issue forwarding, confirm the **Issue Types** selection covers the issue types you are generating.
- Check whether the provider supports the event category in the matrix above. Runtime events are supported only for Datadog.
- If errors persist after credentials are confirmed valid, contact support with the integration name, project, and approximate time window.

## Payload reference[​](#payload-reference)
Outbound events are delivered as JSON. The inner event shape is the same across providers; the outer wrapper is the provider's own log-ingestion format.

A sample **issue event** wrapped for Splunk HEC looks like:

```
{
 "event": {
 "type": "issue",
 "event_title": "Prompt injection detected",
 "event_description": "An incoming prompt matched the prompt-injection rule.",
 "affected_projects": ["Production"],
 "affected_organizations": ["acme"],
 "issue": {
 "issue_id": "iss_001",
 "issue_name": "Prompt injection detected",
 "issue_type": "PolicyViolation",
 "resource": "ai-system/prod-bot",
 "issue_status": "open"
 }
 }
}

```
A sample **incident event** as the inner shape (without provider wrapper) looks like:

```
{
 "type": "incident",
 "event_title": "Repeated prompt injection from same source",
 "event_description": "Multiple related issues clustered into a single incident.",
 "affected_projects": ["Production"],
 "affected_organizations": ["acme"],
 "incident": {
 "incident_code": "inc_001",
 "incident_title": "Repeated prompt injection from same source",
 "incident_description": "Several prompt-injection issues attributed to the same source.",
 "issues": ["iss_001", "iss_002"]
 }
}

```
For Datadog **runtime events** (LLM observability), the payload uses the LLM-observability event shape, with fields covering the conversation history, the prompt and completion tokens, and the associated project. Runtime events are only generated when the project configuration enables runtime forwarding for a Datadog endpoint, and only the Input / Output sides you toggle are exported.

## QRadar Integration[​](#qradar-integration)
There are two methods to send issue and incident data to IBM QRadar:

- Use the **Universal REST API Connector** to pull data into QRadar at regular intervals. This entails writing the integration yourself and creating the correct workflow in QRadar.
- Use the **Panther SIEM integration** to push event and incident data into QRadar via an HTTP receiver in QRadar. This is the method documented below. You will create two new Log Sources (and two Log Source Types if needed) — one for issues and one for incidents.

### QRadar prerequisites[​](#qradar-prerequisites)

- Admin rights to create new log sources in QRadar.
- HTTP Receiver Protocol updated to the latest version. (When auto-update is enabled in QRadar, this is already the case.)
- A PKCS12 certificate chain and password. See the [IBM HTTP Receiver protocol configuration docs](https://www.ibm.com/docs/en/dsm?topic=options-http-receiverprotocol-configuration) for full details.

You can use any valid certificate. For example, [ZeroSSL](https://app.zerossl.com/) offers a free 90-day certificate.

### Convert your certificate to PKCS12[​](#convert-your-certificate-to-pkcs12)
ZeroSSL supplies certificates in PEM by default. To convert a PEM certificate bundle to PKCS12, run:

```
cat certificate.crt ca_bundle.crt &gt; full_chain.crt
openssl pkcs12 -export -out certificate.p12 -inkey private.key -in full_chain.crt

```
Remember the passphrase you set, and transfer the resulting `.p12` file to your QRadar system.

### Configure the QRadar HTTP Receiver log sources[​](#configure-the-qradar-http-receiver-log-sources)
You will repeat these steps **twice** — once to create the Log Source (and, if needed, Log Source Type) for issues, and once for incidents.

- In QRadar, create an HTTP Receiver Log Source.
- Go to **Log Sources &gt; Manage Log Sources &gt; New Log Source &gt; Add a single Log Source**.
- At the bottom of the form, click **Add a new log source type**.
- In the new screen, create the new Log Source Type. Do not alter any of the Log Source Type settings if you plan to create the Custom Event Properties yourself (see the example payloads in the next section). If you prefer Property Auto Detection, enable it here and configure it to your requirements.
- After saving the new Log Source Type, you are returned to the **Create a single Log Source** screen. The new Log Source Type should appear in the search list. If it does not, close the screen and navigate to **Log Sources &gt; Manage Log Sources &gt; New Log Source &gt; Add a single Log Source** again, then search for the name you gave the Log Source Type and select it.
- Click **Select protocol type** and choose **HTTP Receiver**.
- Click **Configure Log Source Parameters**. Give the log source a name and **disable Coalescing Events**. Other settings can be left at default or adapted to your QRadar implementation.
- Click **Configure Protocol Parameters**.
- Fill in a descriptive value for **Log Source Identifier** (for example, `AI Security Issues` or `AI Security Incidents`).
- Leave **Listen Port** at the default.
- Under **HTTP Listener Configuration**, set **Server Certificate** to **PKCS12 Certificate Chain and Password**.
- Set **PKCS12 Server** to the path where you uploaded the `.p12` file, and enter the PKCS12 password you set earlier.
- Under **Authentication Parameters**, set **Use HTTP Authentication Token Header** to **No**. To restrict access to the HTTP Receiver, ask your QRadar admin to configure iptables to allow only the Guardium AI Security source IPs. Request those source IPs from your IBM technical contact.
- Set **Event Parsing Method** to **Event Per JSON Array**.
- Set **JSON Path Expression** to `/"issue_event"` for the issues log source, or `/"incident_event"` for the incidents log source.
- Set **Preserve outer JSON Structure** to **No**.
- Set **Use As A Gateway Log Source** to **No**.
- Set **EPS Throttle** to `5000`.
- Set **Advanced Server Configuration Options** to **Yes**.
- Set **TLS Protocols** to `TLSv1.3`.
- Set **Max POST method Request Length** to `5`.
- Set **Post Request Handler Threads** to `64`.
- Save the Log Source, then repeat the steps for the other event type.

After both log sources are created, perform a deploy from the QRadar admin screen. The log sources are then ready to receive events.

### Configure Atlas side[​](#configure-atlas-side)
Repeat these steps once for each event type (issues and incidents):

- 
Log in to Atlas and go to the **Admin Console**.

- 
Select **SIEM** from the left menu.

- 
Click **Add Integration**.

- 
Choose **Panther** as the integration type and click **Submit**.

- 
Enter the **Integration name** you will use later when configuring per-project event forwarding. Make the name self-explanatory (for example, `QRadar Issues` and `QRadar Incidents`).

- 
Set **HTTP Ingest URL** to the base URL of your QRadar console plus the port the log source listens on — for example, `https://qradar.siem.wow:12469`.

- 
In the **Bearer Token** field, enter a placeholder bearer token. Authentication is disabled on the QRadar HTTP Receiver (you are using IP filtering instead). You can use the following placeholder JWT:

```
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMjM0NTY3ODkwIiwi
bmFtZSI6IkpvaG4gRG9lIiwiYWRtaW4iOnRydWUsImlhdCI6MTUxNjIzOTAyMn0.K
MUFsIDTnFmyG3nMiGM6H9FNFUROf3wh7SmqJp-QV30

```

- 
Click **Submit**. The integration is created. Repeat the steps for the other event type.

Once both integrations exist, choose which events flow to them per project on the SIEM **Configuration** tab. Select the integration for issues and choose which event types are forwarded; repeat for the incidents integration.

### Test the QRadar integration[​](#test-the-qradar-integration)
To verify the integration end-to-end, configure your AI Runtime Protection policies so that they will create issues and/or incidents, then check QRadar to confirm the events arrive and parse correctly. You can use prompts on the runtime to trigger issues, and you can promote an issue to an incident — both flow to QRadar. Expect some delay between event creation in AI Runtime Protection and arrival in QRadar.

If you do not see events arriving in QRadar, you can use `tcpdump` on the QRadar host to confirm that data is being received on the configured ports:

```
tcpdump -i ens18 -vvvs -l -A port &lt;port-of-issues-log-source&gt; or port &lt;port-of-incidents-log-source&gt;

```
