# General

- [](/_docs/)- [Admin Console](/_docs/docs/admin_console/)- GeneralExport PDFOn this page# General
The **General** area of the Admin Console covers tenant identity, the directory of organizations and projects, users, roles, API keys, and the tenant audit trail. This page consolidates settings that the Admin menu surfaces under **System Settings** (Company Profile), **Directory** (Organizations, Projects, Users, User Roles, API Keys), and **Activity Logs** (System Audit Logs). For Notifications, see [Notifications](/_docs/docs/admin_console/notifications).

## Company Profile[​](#company-profile)
Update your customer (tenant) profile and view your customer ID (this may be required when submitting a support ticket to Varonis).

Upload your company's logo to customize reports generated by the system.

You can limit the email domains from which users can access your tenant and view the security admin users on your tenant.

## Organizations[​](#organizations)
Create and edit organizations in the **Organizations** tab. Organizations closely align with business units and often define governance boundaries. You can also see how many projects are under each organization. Define organizations before projects, since creating a new project requires selecting the organization it belongs to.

## Projects[​](#projects)
You can create a project within an organization. Plan your organization and project structure carefully. If you delete a project, you can select a new project to which all existing resources and artifacts are reassigned.

## Users[​](#users)
Invite users using your company's assigned email addresses (the email you select becomes the user's login credential). Assign the roles the user should have, and choose between username + password + MFA authentication or enterprise SSO. For enterprise SSO setup details (Microsoft Entra, Google Workspace, LDAP), see [Authentication](/_docs/docs/platform_services/authentication).

The invited user receives an email to verify their address and an email to accept the invitation. At that point, they set their password and set up MFA in an application such as Google Authenticator or Microsoft Authenticator.

Once a user is created, you can delete the user or reset the user's password (for username + password authentication only; when the user is authenticated by enterprise SSO, Varonis does not have access to passwords).

The system has two distinct access control mechanisms:

- **Role-based permissions.** Roles grant permission to use specific applications, pages, and APIs. A user can only use applications and APIs that their assigned roles allow.
- **Project and organization assignment.** Project and organization assignments grant data-level access. A user can only see resources that belong to projects and organizations they are assigned to. Assigning a user to a project grants access to that project's resources independently of which roles the user holds.

In other words, roles control *what kinds of things* a user can do; project and organization assignments control *which data* the user can do them on.

### Bulk Admin Operations[​](#bulk-admin-operations)
For tenants with many users, the Admin Console supports bulk operations on the user list. You can submit batches for:

- Bulk invitations
- Bulk delete
- Bulk role assignment
- Bulk project assignment
- Bulk organization assignment

Each batch supports up to **100 items**. Bulk operations are processed asynchronously: when you submit a batch, the system accepts the request and starts a background job. You can poll for status to see overall progress and any per-item failures, so a single failing item does not stop the rest of the batch from completing.

### Support Access[​](#support-access)
Varonis support staff can be granted **time-limited elevated access** to your tenant for troubleshooting. Each support access grant:

- Is explicitly created and lasts only for a defined window.
- Is recorded in the audit trail alongside other administrative actions.
- Expires automatically when the time window ends — no manual revocation is required.

You can review active and historical support access grants on your tenant from the Admin Console.

## User Roles[​](#user-roles)
Roles are groups of system permissions and are assigned to users and to API keys. Roles are not hierarchical (a role cannot contain a role), and permissions cannot be assigned directly to users. The system comes with the following pre-built roles:

- **Admin** — Administrator with full access to all system settings, users, and data management.
- **Security Administrator** — Manages security configurations, policies, and controls across systems.
- **Security Analyst** — Monitors, investigates, and responds to security incidents and vulnerabilities.
- **Auditor** — Reviews and assesses compliance with policies, regulations, and system performance.
- **Developer** — Software developer with access to development tools, code, and environments for building applications.
- **Incident Response** — Handles security incidents; responsible for investigating and mitigating security threats.
- **Data Protection** — Manages and enforces policies related to data privacy, protection, and data regulation compliance.
- **Executive** — High-level executive role with access to reports, business-critical data, and oversight of all operations.
- **Limited User** — Restricted access to a limited subset of resources, tools, and data.
- **Prompt Reader** — Access to view prompt inputs and outputs.
- **Guest User** — Limited privileges intended for external participants (for example, completing a TPRM external questionnaire).
- **Firewall Admin** — Administers firewall settings, manages rules, and manages access controls for network traffic.
- **DataDog Admin** — Permissions required for setting up integration with Datadog or the Datadog listener.
- **Splunk Admin** — Permissions required for setting up integration with Splunk HEC or the Splunk HEC listener.

You can create custom roles and assign permissions to them, and then assign them to users.

### Permissions[​](#permissions)
System permissions are assigned on the **Permissions** tab when editing a role (within **User Roles**). Permissions manage both back-end and front-end access. Each API in the system is assigned a permission — for example, a permission controlling whether a role can read scheduled jobs. In addition, each application and front-end tab is given a permission — for example, a permission controlling whether users with the assigned role can access the Technologies page in the AI Inventory application.

## API Keys[​](#api-keys)
Create an API key when your applications or scripts need to call Atlas APIs. Each API key has a type:

- **Custom Integrations** — Most API keys are of this type and are used to call the platform's APIs.
- **Firewall Proxy** — Use this key when you have your own [AI Runtime](/_docs/docs/applications/ai_gateway) deployment or proxy and want to use the control plane APIs for processing prompts and responses to LLMs.
- **Datadog Listener** — Use this key when you want an application to push data to Atlas as it would send logs to Datadog.
- **Splunk Listener** — Use this key when you want an application to push data to Atlas as it would send data to Splunk HEC.
- **Cloud Account Registration** — Use this key for automated registration of cloud accounts.
- **Job Administration** — Use this key for programmatic management of asynchronous jobs (for example, polling the status of bulk operations).

Once you have your API key, assign it the roles that govern the API calls you will use. You only need to assign roles for the **Custom Integrations** type — listener and registration key types automatically carry the matching role.

**Job Administration** keys are system-created only — they cannot be created from the Admin Console UI. They are issued by the platform for programmatic management of asynchronous jobs (for example, polling the status of bulk operations).

## System Audit Logs[​](#system-audit-logs)
Actions performed by users in the application are logged. Because every action in the system corresponds to an API call, the audit trail is shown at the API call level. Each event records the user performing the action, the API called, the API tag, whether it was a GET or POST, and the roles assigned to the user performing the action.

The audit log supports per-API granularity, with filters for time range, user, role, HTTP method, request path, and free-text search. Records are retained for a configurable retention period.
