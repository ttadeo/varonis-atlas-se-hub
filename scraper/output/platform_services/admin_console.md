# Admin Console

- [](/_docs/)- Platform Services- Admin ConsoleOn this page# Admin Console
Open the admin console by selecting it from the top-right menu (under your profile icon).
You need to have either the Admin role or the Security Admin role in order to access the admin console.

## System Settings[​](#system-settings)
Configure system-level settings on the admin console.

### Profile[​](#profile)
Update your customer (tenant) profile and view your customer ID (this may be required when submitting a support ticket to Varonis).

Upload your company's logo to customize reports generated by the system.

You can limit the email domains from which users can access your tenant and view the security admin users on your tenant.

### SIEM Endpoint Configuration[​](#siem-endpoint-configuration)
Add a SIEM integration endpoint for sending issues and events to your SIEM. SIEM integration is supported over HTTPS using an API key. Choose between Splunk HEC, Datadog using API keys, or Panther / any HTTPS/API Bearer-authentication endpoint. To configure the system to send to QRadar, use the Panther integration point. The data is always sent as JSON.

The Admin Console is where you configure the integration endpoint. You can configure as many targets/sinks as required. You then configure exactly which events are sent using these integrations. This configuration is per project and is done on the AI Observability -&gt; Configuration -&gt; SIEM tab.

### QRadar Integration[​](#qradar-integration)
There are two methods to send issue and incident data to IBM QRadar:

- Use the Universal REST API Connector to pull data at regular intervals into QRadar. This entails writing the integration yourself and creating the correct workflow.
- Use the Panther SIEM integration to push event and incident data into QRadar by using an HTTP receiver in QRadar. This is the method described below. Create two new Log Sources and two Log Source Types, one for issues and one for incidents.

QRadar Prerequisites:

- Admin rights to create new log sources.
- HTTP Receiver Protocol updated to the latest version (when auto-update is enabled, this should already be the case).
- PKCS12 Certificate Chain and Password (see [https://www.ibm.com/docs/en/dsm?topic=options-http-receiverprotocol-configuration](https://www.ibm.com/docs/en/dsm?topic=options-http-receiverprotocol-configuration) for full details).

For example, you can get a free 90-day certificate from [https://app.zerossl.com/](https://app.zerossl.com/).
ZeroSSL supplies certificates in PEM by default. To convert your certificate to PKCS12, follow these steps after downloading and extracting the zip file with your certificates:

```
cat certificate.crt ca_bundle.crt &gt; full_chain.crt
openssl pkcs12 -export -out certificate.p12 -inkey
private.key -in full_chain.crt

```
Remember the passphrase you set and transfer the p12 file to your QRadar system.

#### QRadar Configuration Steps:[​](#qradar-configuration-steps)
You will need to do these steps twice. Once to create the Log Source / Type for issues and once for incidents.

- Create an HTTP Receiver Log Source in QRadar
- Go to Log sources &gt; Manage Log Sources &gt; New Log Source &gt; Add a single Log Source.
- On the bottom click “Add a new log source type”.
- In the new screen you will see an option to create a new Log Source Type. Do not alter any of the Log Source Type settings if you want to create the Custom Event Properties yourself as guided later. If you want to enable Property Auto Detection, you can enable it here and configure it with your requirements.
- After filling in all required fields and saving the new Log Source Type, you will be redirected back to the "Create a single Log Source" screen. The newly created Log Source Type should be available in the search list. If it does not appear, close this screen and navigate to Log Sources &gt; Manage Log Sources &gt; New Log Source &gt; Add a single Log Source again, then search for the name you gave the Log Source Type and select it.
- Click on Select protocol type and select HTTP Receiver.
- Click on Configure Log Source Parameters and give it a name and disable Coalescing Events. All other settings can be left as default or adapted to your QRadar implementation.
- Click on Configure Protocol Parameters.
- Fill in a descriptive value for Log Source Identifier (e.g. AI Security Issues and AI Security Incidents).
- Listen Port can be left as is.
- HTTP Listener Configuration - Set PKCS12 Certificate Chain and Password as Server Certificate
- Set the path to where you uploaded the p12 certificate as PKCS12 Server and the PKCS12 password you saved earlier
- Set the Authentication Parameters Use HTTP Authentication Token Header to “NO”. To limit access to the HTTP Receiver, the QRadar admin can configure the iptables firewall to restrict access to only Guardium AI Security IP addresses. Request the source IPs from your IBM technical contact.
- Set Event Parsing Method to Event Per JSON Array.
- Set JSON Path Expression to /"issue_event" for issues OR /"incident_event" for incidents.
- Set Preserve outer JSON Structure to No.
- Set Use As A Gateway Log Source to No.
- Set EPS Throttle to 5000.
- Set Advanced Server Configuration Options to Yes.
- Set TLS Protocols to TLSv1.3.
- Set Max POST method Request Length to 5.
- Set Post Request Handler Threads to 64.
- Save the Log Source and repeat the steps for the other event type.

After creating the Log Sources, perform a deploy from the admin screen. After this, your log sources should be available to receive events.

#### Configuration Steps Within the System:[​](#configuration-steps-within-the-system)

- Login to the system and go to the Admin Console.
- Select SIEM from the menu on the left.
- Select “Add Integration”
- Choose Panther as integration type and click submit.
- Enter the Integration name that you will use later when forwarding issues and incidents (make the name self-explanatory).
- HTTP Ingest URL should be the base URL of your QRadar Console and the port the Log Source has been configured on, e.g., [https://qradar.siem.wow:12469](https://qradar.siem.wow:12469)

#### Test the QRadar integration:[​](#test-the-qradar-integration)
To test whether the integration is working as expected, configure the AI Runtime Protection policies to create issues and/or incidents and check QRadar to confirm the events are received and parsed. You can then use prompts on the runtime to trigger issues and/or events. You can also create an incident from an issue; these will also be sent to QRadar. There is some delay between the creation of events and incidents in AI Runtime Protection and when they are sent to QRadar. If you do not see any events in QRadar, you can use

```
tcpdump -i ens18 -vvvs -l -A port &lt;&lt;port of issue LG &gt;&gt; or port &lt;&lt;port of incident LG&gt;&gt; 

```
to check if any data is received.

### Service Management Configuration[​](#service-management-configuration)
Configure Service Management integration to send AI incidents created within the system to ServiceNow. Note that incidents can also be sent to systems integrated using SIEM integration.

### Evaluator LLM[​](#evaluator-llm)
Various elements in the system use LLMs to generate content and apply reasoning/decision-making. This includes report generation, pentest evaluations, and guardrails that evaluate prompts and responses. You can set which LLM you prefer to use within the context of your system (e.g., what is allowed and what is not allowed), and the system does not ship with any predefined LLMs. Select and upload your API key in the Admin Console.

After you upload your API key and test the connection, you should set up an alert with the LLM provider to ensure that you stay within your budget. Each vendor has a different setup; refer to their documentation for details. For example:

#### AWS Bedrock Setup[​](#aws-bedrock-setup)

- Organize/tag your usage so that you can track the key. Identify which API key or deployment/usage corresponds to that key. Isolate that key’s usage into its own account or project/usage path, or use tagging to mark all invocations tied to that key. Make sure that the usage generated by that key is tagged and that cost allocation is enabled so that you can filter billing/usage by that tag.
- Turn on logging and usage visibility. In Bedrock, enable model invocation logging (to S3 or CloudWatch) so you can see usage details: model ID, token counts, request volumes, etc. In AWS Cost Explorer or Cost &amp; Usage Reports, enable cost allocation tags and make sure your tag is part of the report so you can filter by it. Verify in Cost Explorer that usage tied to your key/tag shows up separately (or at least identify the model/service costs you will associate with it).
- Create an AWS Budget for that usage segment. In the AWS Console, go to Billing → Budgets (via the AWS Budgets service).
Choose the budget type: Cost budget (track dollar spend) or Usage budget (track usage units such as tokens or model invocations) depending on what you want to monitor.
Set the budget period (e.g., monthly) and the amount or usage threshold (e.g., $500/month or 1 million tokens).
In the budget filter settings, apply filters so that the budget only covers the tag you assigned (e.g., Tag: ApiKey = aisecurity) and the service is Bedrock (or more narrowly the model/inference usage) if desired. AWS supports filtering budgets by cost-allocation tags and by service.
- Configure alert thresholds &amp; notifications: Set one or more threshold alerts: e.g., when actual cost &gt; 80% of budget, or forecast cost &gt; 100% of budget.
Choose how you will receive notifications: email and/or Amazon SNS topic so you can hook into Slack, Teams, or an automation.
Optionally, you can also configure budget actions: when the budget is exceeded, AWS can perform actions (e.g., apply an IAM policy or service control policy), though note it may not stop Bedrock model usage automatically unless you build automation.

After creating the budget, monitor usage and filter by your tag to ensure that the budget is correctly capturing the usage of that key. If you notice drift (usage from other keys creeping into the same tag, or some usage not tagged), adjust your tagging or budget filter accordingly. Review your model usage and cost (via Cost Explorer and AWS Budgets dashboards) to verify that alerts will fire when expected.

If you want enforcement (i.e., automatically disable or throttle the key once the spend threshold is reached), you will need to build a small automation: e.g., budget notification -&gt; Lambda or SNS subscriber -&gt; disable key / stop service / change IAM role.

#### Azure Open AI Setup[​](#azure-open-ai-setup)
Azure Cost Management is a sophisticated subsystem that lets you monitor and alert on usage and forecasts; [refer to Azure documentation for full details](https://learn.microsoft.com/en-us/azure/cost-management-billing/costs/tutorial-acm-create-budgets?utm_source=chatgpt.com&amp;tabs=psbudget). One simple method is to create a budget called Varonis or Guardium AI Security that includes the appropriate resource group or management group:

- In the Azure Portal, navigate to Cost Management + Billing.
- Choose the scope you want to monitor such as a resource group or a management group.
- In that scope, go to Budgets (or “Create budget”).
- Define the budget: Give it a name, choose period (monthly, quarterly, annually) for reset, set the budget amount (e.g., $100/month).
- Add filters so the budget applies just to your Azure OpenAI usage (or whatever subset you care about). For example: Service = AI Security, MeterSubCategory = Azure OpenAI.
- Configure alert thresholds: For “Actual cost” (e.g., when actual spending reaches 80% of the budget). Use “Forecast cost” (e.g., when Azure projects that you will exceed 100% of the budget) if desired.
- Add email addresses (and optionally action groups) to receive the alert.

#### OpenAI Setup[​](#openai-setup)
OpenAI does not support alerts per API key, only per project. Therefore, it is recommended that you create a project with a descriptive name such as Varonis or Guardium AI Security within your OpenAI account, and create the API key you will use within that project. Then:

- Go to the OpenAI Platform and sign in.
- Select the organization → then go to the project for which you want alerts.
- In that project’s settings, go to “Limits” (or “Usage &amp; limits” / “Billing &amp; usage”).
- Under the budget/usage section you’ll see options such as:
a. Monthly budget (in dollars).
b. Notification threshold(s) — e.g., alert at 80% of budget.
- Configure the threshold(s) and save. When usage exceeds the threshold, you’ll get an email to the org/project owners.

#### Google Gemini Setup[​](#google-gemini-setup)
Under your Google Cloud project:

- Associate the API key with a dedicated resource or label it. Consider using a distinct project for that key (e.g., Varonis or Guardium AI Security). Alternatively (or in addition), use a label on the resources that the key uses (for example: gemini_key=key-1234 or usage_group=ai-security). Labels propagate into cost/usage data for filtering. Make sure you consistently use that label on all resources tied to that API key (deployments, endpoints, service accounts, etc.).
- Make sure billing export or usage tracking is set up. Ensure your Google Cloud billing data is visible (via reports) so you can slice by label, project, service, and SKU. Check that your Gemini usage shows up under a service or SKU you can filter.
- Create a budget in Billing → Budgets &amp; alerts. In the Google Cloud console go to Billing → Budgets &amp; alerts → Create budget. For Scope, select the billing account (or the specific project) that the key lives in. Set the Budget amount (e.g., $100/month). In Filters (under “Scope” or “budgetFilter”), set: Project = the project tied to the API key (if dedicated). Service = the Gemini/Generative AI service if possible. Labels = the key label you applied (for example: gemini_key=key-1234)
- Set one or more Threshold rules, e.g.: 50% of budget → send alert
- Configure notification recipients (email, and/or Pub/Sub for automation).
- Save the budget and monitor.

Once saved, you will receive alert emails when the filtered spend crosses your thresholds. Use Reports -&gt; Filter by project/service/label to verify that you are actually capturing the spend for that key. If costs appear from unintended resources, adjust labels/filters.

Optional automation for enforcement: If you want to automatically stop usage once the budget is exceeded, use the budget’s Pub/Sub notification to trigger a Cloud Function. The function can disable the API key or disable the resource/service endpoint tied to that key.

## Directory[​](#directory)
Admins manage organizational hierarchies and how projects are organized. Access control, policies, and more are governed by organizations and projects, as assets and resources belong to projects.

### Organizations[​](#organizations)
Create and edit organizations in the Organizations tab. Organizations closely align with business units and often define governance boundaries. You can also see how many projects are under each organization. Organizations should be defined before projects since creating a new project is done by selecting the organization it belongs to.

### Projects[​](#projects)
You can create a project within an organization. Plan your organization and project structure carefully. If you delete a project you can select a new project to which all existing resources and artifacts are assigned.

### Users[​](#users)
Invite users using your company's assigned email addresses (the email you select will become the user's login credential). Assign the roles the user should have and select whether to use username/password/MFA authentication or Google OAuth2 authentication. The invited user will receive an email to verify their address and an email to accept the invitation. At that point, they will set their password and set up MFA in an application such as Google Authenticator or Microsoft Authenticator.

Once a user is created, you can delete the user or reset the user's password (when using username/password authentication only; when the user is authenticated by enterprise authentication, Varonis does not have access to passwords).

There are two access control mechanisms within the system. Roles are used for permissions of applications and organizations and projects control access to the data and resources within projects. A user can only see projects they belong to and can only use applications and APIs that their roles allow.

### User Roles[​](#user-roles)
Roles are groups of system permissions and are assigned to users and to API keys. Roles are not hierarchical (i.e. a role cannot contain a role) and permissions cannot be assigned directly to users. The system comes with the following pre-built roles (and the intended purpose):

- Admin - Administrator with full access to all system settings, users, and data management.
- Security Administrator - Security Administrator responsible for managing security configurations, policies, and controls across systems.
- Security Analyst - Analyst focused on monitoring, investigating, and responding to security incidents and vulnerabilities.
- Auditor - Responsible for reviewing and assessing compliance with policies, regulations, and system performance.
- Developer - Software developer with access to development tools, code, and environments for building applications.
- Incident Response - Handles security incidents, responsible for investigating and mitigating security threats.
- Data Protection - Manages and enforces policies related to data privacy, protection, and compliance with data regulations.
- Executive - High-level executive role with access to reports, business-critical data, and oversight of all operations.
- Limited User - Read only access to features
- Internal - Reserved for system maintenance only
- Firewall Admin - Administers firewall settings, manages rules and access controls to secure network traffic.
- DataDog Admin - Permissions required for setting up integration with Datadog or the Datadog listener
- Splunk Admin - Permissions required for setting up integration with Splunk HEC or the Splunk HEC listener

In addition, the following roles govern access to the Observability layer of the system:

- ObservabilityAdministrator - Full access to AI Observability and Report features, plus the ability to view Varonis Audit Logs in the Admin Console. Ideal for senior security analysts and managers overseeing observability operations.
- ObservabilityViewer - Read-only access to all AI Observability and Report pages. Perfect for team members who need to monitor and analyze observability data without making changes.
- ObservabilityEditor - Full access to view and edit all AI Observability and Report pages. Suitable for security analysts and engineers who actively manage and configure observability settings.
- ObservabilityAuditor - Specialized access to view Varonis Audit Logs in the Admin Console. Designed for compliance officers and external auditors who need to review system activities and changes.

You can create custom roles and assign permissions to them, and then assign them to users.

### Permissions[​](#permissions)
System permissions are assigned on the Permissions tab when editing a role (within User Roles). Permissions manage both back-end and front-end access. Each API in the system is assigned a permission -- e.g., GET /v1/scheduling-jobs/your-customer-id/jobs returns all scheduled jobs. In addition, each application and front-end tab is given a permission -- e.g., ai-inventory--technologies controls whether users with the assigned role can access the Technologies page in the AI Inventory application.

### API Keys[​](#api-keys)
Create an API key when your applications/scripts need to call TRiSM Hub APIs. Each API key has a type as follows:

- Custom Integrations - Most API keys will be of this type and would be used to call the platform's APIs.
- Splunk Listener - Use this key when you want an application to push data to the TRiSM Hub as it would send data to Splunk HEC.
- Datadog Listener - Use this key when you want an application to push data to the TRiSM Hub as it would send logs to Datadog.
- Runtime Proxy - Use this key when you have your own AI Runtime Protection / runtime / proxy but would like to use the control plane APIs for processing prompts and/or responses to LLMs.

Once you have your API key, assign it the roles that govern the API calls you will use. You only need to assign roles for the Custom Integrations type -- a Splunk Listener key will always have the SplunkAdmin role (and only that role), and so forth.

### Audit Logs[​](#audit-logs)
Actions performed by users in the application are logged. Because everything in the system is an API call, the audit trail is shown at the API call level. Each event records the user performing the action, the API called, the API tag, whether it was a GET or POST, and the roles assigned to the user performing the action.
